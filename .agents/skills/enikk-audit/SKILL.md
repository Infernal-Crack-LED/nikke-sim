# enikk audit — top-ranker team + roster snapshots

## "the enikk list" — what it means

When the owner says **"the enikk list"**, **"enikk supported list"**,
**"enikk-proven"**, or anything of that shape, they mean the
**`## All raids — NIKKE union`** section of
[docs/enikk-top100-audit.md](../../../docs/enikk-top100-audit.md) — the deduped
union of every NIKKE that shows up in the top-100 rankers' teams across all
audited raids. That union IS the enikk-supported roster. (It is regenerated by
this skill's audit script — see below — so treat the doc as the current
snapshot, not a hand-maintained list.)

That same union is mirrored machine-readably in
[data/enikk-supported.json](../../../data/enikk-supported.json) (a `names` array),
regenerated in lockstep with the MD by the audit script's `SUPPORTED=` output.
`src/data/sync.ts` reads it as a second-stage roster keep-filter: on every sync it
keeps a unit **iff** its name (`(Treasure)` stripped) is in that list OR the unit
has a hand-tuned override — so the enikk prune survives re-syncs instead of being
silently re-added. Regenerate the MD and the JSON together, never hand-edit either.

## What this is for

Pull what the strongest players actually field from enikk.app's solo-raid
leaderboards, so the battery/testing work is anchored on the live meta rather
than guesswork. Two uses:

1. **Roster audit** (`scripts/enikk/roster-audit.ts`) — for each raid, dedup
   the top-N rankers' teams and list every NIKKE in what remains, flagging
   which the sim models. Answers "what units matter this season, and which are
   we blind to?" (the unmodeled `*` set is the override-backlog priority list).
2. **Anchor sourcing** — the same SRRankings data seeds the realistic battery
   anchors (`/sim-battery`) and the Testing Requests page (teams featuring
   units the owner doesn't own). Reuse a cached pull instead of re-fetching.

## The data source

enikk.app is a Next.js app over GraphQL at `https://enikk.app/api/webapp`.
Key query for this work:

```graphql
query SRRankings($raid: Float!, $all: Boolean) {
  SRRankings(raid: $raid, all: $all) { damage teams }
}
```

- The response array is the leaderboard **already sorted by damage descending**
  — so "top 100 rankers" = the first 100 rows. (The `rank` field is NOT a
  global rank; it maxes out around 50 and repeats — do not sort by it.)
- Each row (one ranker) carries up to 5 saved `teams`; each team has
  `characters` (5 display names, slot order) plus `count`/`cp`/`cores`.
- Raid → boss element: `soloraids { raid_number monster_obj }`, read
  `monster_obj.element_id.weak_element_id`. Current mapping lives in
  `RAID_META` in the audit script — extend it when a new raid lands.

## The support policy this audit drives (DECISIONS 2026-07-14)

The supported roster IS the enikk-proven list (the `## All raids — NIKKE union`
section — see "the enikk list" above) plus every hand-tuned override we already
have. When applying the audit:

1. **Model** any enikk-proven unit lacking a hand-tuned override
   (`src/skills/overrides/*.json`) — fetch/add base data first if it isn't in
   `characters.json`.
2. **Remove** from the sim (drop from `characters.json`) any unit that is NOT
   enikk-proven AND has no hand-tuned override — the parse-only units that never
   show up in the top-100 meta.
3. **Keep rule — never remove a unit that has a hand-tuned override**, even if it
   later falls out of the enikk-proven list. (The protected set is hand-tuned
   overrides specifically, NOT parse-only `characters.json` units — the sim can
   parse-run any character without an override, so "modeled" alone is ambiguous.)

This policy is already applied to `data/characters.json`: the 16 parse-only
units that were neither enikk-proven nor hand-tuned have been pruned (101→85
units), and the `sync.ts` keep-filter (above) keeps the prune durable across
re-syncs.

Note the audit's `*` flag means "no hand-tuned override" — that unit may still be
parse-runnable (in `characters.json`) or genuinely absent; check which before
modeling vs. treating as new.

## Running the roster audit

```sh
npx tsx scripts/enikk/roster-audit.ts                       # live fetch, all 5 raids, top 100
TOP=50 RAIDS=38 npx tsx scripts/enikk/roster-audit.ts       # one new raid, top 50
ENIKK_CACHE=<dir> npx tsx scripts/enikk/roster-audit.ts     # read/write raw JSON (offline reuse)
OUT=<f>.json MD=<f>.md npx tsx scripts/enikk/roster-audit.ts  # structured + readable dumps
SUPPORTED=data/enikk-supported.json npx tsx scripts/enikk/roster-audit.ts  # keep-filter mirror for sync.ts
```

**Canonical regeneration** (refresh the snapshot + the sync keep-filter together):

```sh
MD=docs/enikk-top100-audit.md SUPPORTED=data/enikk-supported.json \
  ENIKK_CACHE=<dir> npx tsx scripts/enikk/roster-audit.ts
```

- **Dedup semantics**: teams are deduped by the SET of 5 units (slot order
  ignored — same five units is one comp); the kept `count` is how many of the
  top-N rankers ran it, and the representative slot order is first-seen.
- **`ENIKK_CACHE`**: with it set, each raid's raw GraphQL response is cached
  there and reused on the next run — set it to a scratch dir to avoid
  re-fetching within a session, or to seed the audit from an earlier pull.
  Cache files are named `enikk-r<raid>-rankings.json`.
- Live fetch needs network. Cache files from a prior `curl` pull work as long
  as they're the `{ data: { SRRankings: [...] } }` shape with `teams` present.

## Refreshing for a new raid

1. Add the raid to `RAID_META` (number → `{label, boss}`) — get the boss from
   the `soloraids` query's `weak_element_id`.
2. Run the audit with `RAIDS=<new number>` (and `MD=`/`OUT=` to snapshot).
3. The `*`-flagged unmodeled units in the new raid are the override-writing
   priority; the modeled ones can seed new `/sim-battery` anchors.
4. A new raid changes the union, so **regenerate the full snapshot + keep-filter
   together** with the canonical command above (`MD=…docs/enikk-top100-audit.md
   SUPPORTED=data/enikk-supported.json … RAIDS=<all raids incl. the new one>`) —
   otherwise `data/enikk-supported.json` (and the `sync.ts` prune) goes stale
   against the new meta. Then re-apply the support policy: model any newly
   enikk-proven unit, and the next `npm run sync` will keep them.

## Output notes

- `docs/enikk-top100-audit.md` is a **regenerable snapshot**, not a source of
  truth — it goes stale when enikk updates. Regenerate rather than hand-edit;
  it carries a header saying so.
- Name variants matter: enikk lists base and alt units separately (e.g.
  "Scarlet" vs "Scarlet: Black Shadow", "Guillotine" vs "Guillotine: Winter
  Slayer", "Rei" vs "Rei (Tentative Name)"). The name→slug map strips only
  " (Treasure)"; anything else that shows `*` is genuinely not in our roster.
