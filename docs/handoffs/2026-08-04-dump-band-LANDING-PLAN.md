## 1. The defect

`count-pellets.py:1865` writes a dump's `frame_counts` as `{white, red, marker}` — **dropping
`band`**, even though the value is right there (`:1847`'s per-backend template already carries
`"band": 0` and `dict(fr)` copies the real one from `_frame_pellet_counts`).

`debounce_shots` falls back to **pre-hybrid** behaviour when no frame carries a `band` key
(`count-pellets.py:598`, `has_band`). Therefore:

⚑ **Every dump produced by `--dump-tracks` replays as if the 2026-08-04 hybrid landing never
happened.** Any future audit against fresh footage silently scores the OLD representative-frame rule
while appearing to test production. This does **not** affect the production reader — `read-pellets.ts`
parses `--temporal` stdout (`:1935`), which does carry `band`.

**This is a silent production/analysis divergence**, the failure class that cost this thread two
sessions on §8H's phantom tie-break and that §17 recorded as "a loud failure turned into a silent one".

## 2. The change

1. **`count-pellets.py:1865`** — add `"band": r["opencv"]["band"]` to the dumped `frame_counts`.
2. **`analyze-pellet-tracks.py:3015`** (`_rep_slim_dump`'s row builder) — carry `band` when the
   source dump has it, so the fix is not immediately undone at fixture-build time.
3. **Its readers** — `:3021` and `:3546` currently do a hard 3-unpack (`for w, r, m in …`). They must
   accept **3-wide OR 4-wide** rows.

⚑ **A 3-wide row means `band` is UNKNOWN and the key must be OMITTED, never defaulted to 0.**
`has_band` tests key _presence_; a fabricated `band: 0` would flip a pre-hybrid replay into the
hybrid path with an all-zero band series. (`_plateau_rep` would return `None` and fall back, so the
answer would likely survive — but the mechanism would be wrong, and "likely survives" is not a
guarantee anyone should be relying on.)
