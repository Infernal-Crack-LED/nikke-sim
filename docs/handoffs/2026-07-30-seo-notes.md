## 1. GSC "Page with redirect" — not a defect, no action needed

GSC lists `http://nikkesim.app/` and `http://www.nikkesim.app/` as not indexable under "Page with
redirect." Verified live (2026-07-30):

| URL                         | Result                                          |
| --------------------------- | ----------------------------------------------- |
| `http://nikkesim.app/`      | 301 → `https://nikkesim.app/` (canonical)       |
| `http://www.nikkesim.app/`  | 301 → `https://www.nikkesim.app/`               |
| `https://www.nikkesim.app/` | 200 (live page, NOT a further redirect to apex) |
| `https://nikkesim.app/`     | 200 (canonical)                                 |

This status is Google **confirming the redirect worked and correctly excluding the non-canonical
URL from the index** — not an error. No fix required for the http:// entries.

One real (but minor) wrinkle: `https://www.nikkesim.app/` doesn't redirect to the apex, it serves
the app directly as a live 200 — Railway has both `nikkesim.app` and `www.nikkesim.app` attached as
domains to the same service. This is currently harmless because `web/index.html` hardcodes
`<link rel="canonical" href="https://nikkesim.app/">`, so Google should treat the `www` host as a
duplicate and canonicalize to the apex regardless of which host served the request.

**Optional cleanup (low prio, cosmetic):** add a `www` → apex redirect at the Railway/DNS level so
`www` doesn't serve a live duplicate at all. Belt-and-suspenders only; the canonical tag already
covers the substance of it.

## 2. The SPA/SSR gap — what it would and wouldn't buy

`web/index.html` ships full meta tags in the static HTML (title, description, OG, Twitter card,
JSON-LD) — those are visible to any crawler today, JS or not. What's missing from the raw HTML is
the actual page body: DPS/overload tables, unit data, mechanics writeups, FAQ answers — all
rendered client-side by React after hydration.

Verified 2026-07-30: `nikkesim.app/mechanics` **is already indexed by Google** (surfaces in search
for "NIKKE Solo Raid Sim overload optimizer"), because Googlebot executes JS in a second-wave
render pass before indexing. That pass can lag hours-to-weeks behind the initial crawl, but Google
does eventually see the rendered content — this is not "invisible to Google" the way it reads on
first pass.

**Correction to the original framing:** Google's AI Overview is generated from Google's own Search
index — the same index that already contains the JS-rendered content. So AI Overview citation is
gated by normal ranking (does Google judge this page the best answer to the query, against
higher-authority competitors like nikke.gg / Prydwen / bittopup), **not** by rendering. SSR/SSG
would not move that needle — it doesn't make Google rank the page higher, just removes a delay tax
that mostly doesn't apply to Google specifically.

Where SSR/prerendering **does** directly matter: the other AI-answer-engine crawlers already
allowlisted in `web/public/robots.txt` (GPTBot, ChatGPT-User, OAI-SearchBot, ClaudeBot,
PerplexityBot) largely do raw-HTML fetches without executing JS, and build their own separate
indexes rather than reusing Google's. For those, the mechanics/FAQ content is genuinely invisible
today beyond the meta description.

**Decision framing:** full SSR (Next.js/Remix-style rewrite of the Vite/React SPA) is a real
migration, not a quick patch. A cheaper middle path if this is ever worth doing: keep the
interactive calculator as a client-rendered SPA (nobody needs to cite "the calculator" itself — a
tool isn't quotable text), but prerender/statically generate just the content pages that are
actually citation-worthy (mechanics docs, FAQ) via something like `vite-plugin-ssr`, Astro islands,
or a build-time prerender step for those specific routes.

**Status: parked, low priority.** Owner is not sure this is worth the effort — revisit only if
AI-citation / organic search traffic to the docs content becomes something worth optimizing for
(vs. the site's current traffic mostly coming through Discord/community links).
